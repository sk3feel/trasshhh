## Что было фиксировано и что изменено
Исходный живой runner всегда выбирал expanded для большой модели, если кэш usable; A/B на выбор данных C не влияли. Исходный Python-процесс не перезапускался и его уже загруженный код не подменялся. Добавлен bounded review gate только в будущих workers C: до90с внутри бюджета C, без обучения. Итоговое ab_data_decision.json явно выбирает current2,368,669 вместо исходного expanded5,820,047; применённые fingerprint и пути записаны в configs/C_large_{smoke,train}.effective.json и runs/C_large_scratch/intent.json. Файл configs/C_large_scratch.json от runner отражает первоначальный план, effective/intent — фактический запуск.

Решение: использовать доказавший работоспособность current для одной большой модели с нуля в ограниченные4 часа. A улучшила основной greedy до332; B дала326 и не превзошла330, несмотря на большее число предъявлений. Более низкий CE B не считается победой по численному качеству. Это осторожный выбор бюджета, НЕ доказательство вреда expanded и НЕ уверенность, что поздний resume20.1M предсказывает обучение34.1M с нуля. Новый большой опыт не является чистой архитектурной абляцией относительно долго обучавшегося baseline.

## Скорость и память

Условия train batch64/LR1e-4/model/optimizer были одинаковыми, реальные предъявления различались.

Для C smoke batch32, fallback16 только при проблеме памяти, без подбора LR. Добавлено освобождение неиспользуемого CUDA-кэша при reservation>8.5GiB в логируемых шагах. Это также применяется к будущему D; A/B задним числом не изменялись. Teacher-forcing CE для d512 использует batch32 (или16 при fallback), токен-взвешивание прежнее; возможны малые FP16 отличия от batch64. Основная greedy генерация всегда прежний batch32/max256/512 задач/493 знаменатель. Память smoke — PyTorch allocated/reserved, НЕ отдельный физический замер.

## Как выбирается продолжение
Живой runner ранжирует успешные A/B/C по best greedy correct, при равенстве по меньшему CE. Продолжает победителя, если correct>330. Только если НИКТО не превзошёл330, возможен fallback на C при улучшении и CE, и correct между двумя последними оценками. Поскольку A=332, этот fallback уже не сработает: если C ниже332, даже при положительной динамике, D автоматически не переключится на неё. Это явное ограничение текущего правила; раннее отставание не сокращает сам четырёхчасовой C. Никаких новых гипотез для D не добавлено.
